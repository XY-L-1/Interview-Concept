How Interview Concept is structured

A practical guide to the product boundaries, folder layout, content versioning, request flow, and the first implemented learning slice. Read this as the “why” behind the code.

Mental model Folders Boundaries Content model Routes Roadmap
01 · Mental model

One application, with explicit internal ownership

The product is a modular monolith. It is deployed as one Next.js application and will initially use one PostgreSQL database. “Modular” means each product area owns its rules and data; “monolith” means a small team does not pay the operational cost of coordinating multiple services.

App routes Read URL parameters and compose the page or HTTP response.
Module API Exposes the small set of operations another layer may call.
Domain rules Owns ordering, publication, versioning, and learner rules.
Platform adapters Connects PostgreSQL, auth, jobs, and observability later.
Core rule: routes do not contain business rules and do not call their own HTTP API. Server Components call a module’s public application functions directly.

Implementation status: today the anonymous public reader is implemented with typed file-backed content. PostgreSQL, authentication, private read paths, editorial commands, search, and AI persistence below are the planned architecture, not completed product features.

Where code belongs

│   ├── discovery/          Search projection and ranking

│   └── ai/                 Generated artifacts and provenance

tests/                      Cross-module and end-to-end behavior
docs/                       Version-controlled architecture decisions

A course-specific component stays in modules/content. It should move to shared/ui only after multiple product modules genuinely need the same domain-neutral component.

03 · Product boundaries

Public content and private data never share a read path

This is the enforced design boundary for upcoming modules. The current slice implements only the public path; the private paths are intentionally still placeholders.

Data class Examples Important rule
Public Published courses, sections, questions, editorial answers May be statically generated or shared-cacheable.
Staff-private Drafts, reviews, previews, publication audit history Requires staff authorization below the routing layer.
Learner-private Progress, confidence, bookmarks, notes, last viewed Owner-scoped and never placed in a shared public cache.
Generated-private AI prompts, outputs, model and cost provenance Never becomes a canonical answer automatically.

Content module

Owns the curriculum and the official bilingual teaching material. Editorial publishing changes what public readers see.

Learning module (planned)

Owns a learner’s relationship to a stable question: progress, confidence, bookmark state, and eventually repetition history.

Discovery module (planned)

Owns a rebuildable search projection containing only currently published canonical content.

AI module (planned)

Owns generated suggestions and provenance. An editor must publish a canonical content revision before AI material becomes public.

04 · Content model

Stable identities; immutable published release tree

Learner data should survive an editorial rewrite. Therefore a question has a stable ID, while placement, ordering, wording, and both answer experiences are fixed by immutable published revisions.

Stable identities

  • Course, section, and question IDs
  • Immutable routing slugs and explicit course ownership
  • Learner progress references the question ID
  • The course points to its current release
  • No mutable placement or answer fields
→

Immutable course release tree

  • Course order and ordered section revisions
  • Each section fixes its ordered question revisions
  • Each question fixes difficulty and its English answer
  • 同一题目版本固定中文定义、机制、示例、场景、误区、追问和总结
English and Chinese are authored for different jobs. The English answer is concise and natural for a real interview. The Chinese material teaches the concept deeply; it is not a line-by-line translation.

Teaching examples use explicit formats: code examples support TSX, TypeScript, JavaScript, and Java, while prose and diagram-description examples cover topics such as System Design without pretending every explanation is source code.

The planned publishing command will create changed question and section revisions, then a new immutable course revision that fixes the complete curriculum. Only the stable course pointer will move. Old releases remain reconstructable, while learner progress can keep referencing the stable question ID and record the last revision seen.

For the current file-backed source, validatePublishedContentData acts like database constraints: the build fails early for broken IDs or references, invalid revision numbers or slugs, ambiguous ordering, duplicate course/question routes, and orphaned published revisions.

05 · First vertical slice

The smallest end-to-end learning experience

URL Responsibility
/ List currently published courses.
/courses/react Show ordered sections and questions for React.
/courses/react/questions/<question-slug> Render one atomic bilingual revision and previous/next links.

Section slugs are deliberately absent from question URLs. Moving a question between sections preserves a learner’s saved link because its routing slug belongs to the stable question identity. Slug renaming is intentionally unsupported in the MVP; if introduced later, old slugs must remain as redirect aliases. The content module calculates section context and previous/next navigation from the release tree.

Request example

  1. Next.js matches the course and question URL parameters.
  2. The route calls the content module’s public reader.
  3. The reader resolves the stable course’s published revision pointer.
  4. It traverses that release’s exact ordered section and question revision IDs, then matches the stable question slug.
  5. The route renders the returned public view model.
  6. An unknown or unpublished slug becomes a real 404.
06 · Growth path

What comes next—and what does not come early

  1. Now: validate the public course → question → bilingual answer workflow with typed file-backed content.
  2. Next: introduce PostgreSQL tables and an editorial publishing path behind the same content module API.
  3. Then: add identity and owner-scoped progress, confidence, and bookmarks.
  4. After enough content: build the discovery search projection and relevance rules.
  5. Later: notes, flashcards, spaced repetition, mock interviews, and reviewed AI follow-up suggestions.
A service should split out only when it has an independent scaling profile, operational requirement, or team ownership boundary. Until then, keeping one deployable application is the simpler and safer production choice.
